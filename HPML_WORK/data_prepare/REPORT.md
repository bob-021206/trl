# 多轮工具调用 GRPO 优化：测试数据与模型选型报告

## 1. 目的

我们要优化的是 TRL `GRPOTrainer` 在 `vllm_mode="colocate"` + sleep mode 下的多轮工具调用：

- **Tech 1**：避免每轮工具调用后重新加载一次权重。
- **Tech 2**：跨轮保留 vLLM 的前缀缓存（KV cache）。

两项优化的收益都取决于「每条样本几轮」「每轮工具返回多长」「系统提示多长」。所以测试数据要做到：**轮数由数据决定而不是由模型决定**，长度可以精确控制，这样耗时差异才能归因到具体因素上。

## 2. 数据集设计

一共三套数据（W = Workload），从「可控」到「真实」排开。

| | W1 链式算术 | W2 多跳检索 | W3 MuSiQue |
|---|---|---|---|
| 来源 | 程序生成 | 程序生成的虚构知识库（5000 个实体） | 公开多跳问答数据集（validation 集） |
| 工具 | `get_op(op_id)` | `search(query)` | `search(query)` |
| 任务 | 起始数 + 一串加减操作；每一步的操作和下一步的 id 只出现在上一步的工具返回里，必须一步一步调 | 从问题里的实体出发，每份文档里才有下一个实体，跳 K 次后回答 | 每题自带 20 段文字，在里面检索后回答 |
| 轮数 K | 固定：2, 4, 8, 16 | 固定：2, 3, 4, 6 | 不固定（标注的跳数 2–4，实际搜几次由模型决定） |
| 每轮返回长度 L_obs | 精确 64 / 256 / 1024 token | 约 266 / 773 / 1281（返回 1 / 3 / 5 篇文档） | 不固定（136–1185） |
| 系统提示长度 P | 精确 256 / 2048 | 精确 512 | 精确 512 |
| 格子数 × 样本数 | 24 × 512 | 12 × 512 | 3 格（512 / 512 / 332） |
| 定位 | **主实验**：扫 K、L_obs、P | 补充：更接近真实的长上下文检索 | 展示：证明不只在人造数据上有效 |

几点设计细节：

- 所有长度都按 Qwen3 的 chat template（`enable_thinking=False`）、按 TRL 实际拼接 token 的方式测量。L_obs 指每轮工具调用后追加的全部 token（工具返回 + 模板 + 下一轮生成前缀），其中约 34 个是固定开销。
- 长度靠 wikitext-2 的英文文本填充；系统提示在一个格子内所有样本相同，和真实 agent 一样。
- W1 题面要求模型每一步写出当前值（如 `45 - 2 = 43`），最后一步的工具返回会说明「这是最后一步」。
- W3 的答对判定是宽松匹配：标准答案或别名（归一化后）出现在模型答案里即算对。

### 数据检查

`w*_check.py` 在 CPU 上逐条验证：

- 答案独立重算一遍，和数据里存的一致。
- 每个 id / 实体只能从上一步得到，不能跳步或并行调用。
- 所有长度参数精确。
- 一个只读工具返回的脚本化策略恰好调用 K 次、拿满分。
- 用相同种子重新生成，得到完全一样的数据（sha256 一致）。

全部 39 个格子都通过检查。

## 3. 使用方法

所有文件都在 `HPML_WORK/data/` 下，生成的数据在 `HPML_WORK/data/out/`（约 264 MB，不进 git）。

```bash
bash HPML_WORK/data/generate_all.sh             # 一键生成并检查三套数据（只用 CPU）
bash HPML_WORK/data/generate_all.sh --install   # 先装好固定版本的依赖
```

训练时，每个格子目录可以直接用 `datasets.load_from_disk` 读取。目录下的 `meta.json` 里记录了这个格子的 GRPO 长度上限（`max_completion_length`、`vllm_max_model_length`、`max_tool_calling_iterations`），直接展开到 `GRPOConfig` 里即可。环境类和奖励函数从 `w*_env.py` 导入。完整示例见 `README.md`。

`smoke_test.py` 把三套数据都接到了 GRPOTrainer 上：

```bash
# 0.6B 每个格子跑 1 步，检查能不能跑通
python HPML_WORK/data/smoke_test.py HPML_WORK/data/out/w*/K*
# 4B + LoRA 跑 50 步
python HPML_WORK/data/smoke_test.py HPML_WORK/data/out/w1/K8_L256_P256 \
    --model Qwen/Qwen3-4B --lora-r 16 --learning-rate 1e-5 --max-steps 50
```

## 4. 模型测试结果

### 4.1 能不能跑通（Qwen3-0.6B，每格 1 步 GRPO）

39 个格子全部跑通：没有工具调用报错，没有回答被长度上限截断。但未训练的 0.6B 不会按要求调工具：

| 数据 | 跟完整条链的比例 | 每样本工具调用次数 | 答对率 |
|---|---|---|---|
| W1 | 0–38%，多数低于 20% | 0–5，经常不调就直接作答 | 约 0 |
| W2 | 0–19%，K ≥ 4 时为 0 | 0.9–2.4，多数搜一次就停 | 约 0 |
| W3 | 0 | 0.06–0.3，凭记忆作答 | 约 0 |

### 4.2 各尺寸模型的能力（只推理，贪心解码，每格 32 条）

| 模型 | W1 K4 答对 / 跟完链 | W1 K8 答对 / 跟完链 | W2 K3 答对 | W3 K2 答对 |
|---|---|---|---|---|
| Qwen3-0.6B | 0% / 0%（照抄题面示例，不调工具） | 0% / 0% | 0% | 0% |
| Qwen3-1.7B | 0% / 94%（跟得上，但不写中间值） | 0% / 94% | 6% | 0% |
| Qwen3-4B | 47% / 100% | 59% / 97% | 47% | 19% |

4B 能逐步写出中间值，最后的答案和数据里存的标签一致，说明数据本身没问题，0.6B 和 1.7B 答对率低是模型能力不够。

### 4.3 GRPO 训练 50 步（W1 K8_L256_P256，每步 16 条 rollout）

| | Qwen3-0.6B 全参数 | Qwen3-4B + LoRA（rank 16） |
|---|---|---|
| 奖励 | 答对 + 跟链比例（权重 1:1） | 只用答对 |
| 学习率 | 3e-6 | 1e-5 |
| 跟链比例 | 第 1 步 0 → 第 10 步 0.88 → 第 11 步起多数为 1.0，最后 10 步里 8 步为 1.0 | 50 步里 45 步为 1.0，最低 0.78 |
| 每样本工具调用 | 最后 10 步 7.8–8.3 | 基本为 8.0–8.3，个别步 6.6、7.6 |
| 答对率 | 一直约 0 | 1–10 步平均 26% → 11–20 步 54% → 21–30 步 88% → 最后 20 步平均 97%，其中 15 步为 100% |
| 每步耗时 | 27–37 秒（第 1 步不调工具，6 秒；共 1726 秒） | 69–91 秒（共 4208 秒） |
| 显存峰值（PyTorch 统计） | 32.8 GB | 40.6 GB |

## 5. 硬件与软件环境

| 项目 | 配置 |
|---|---|
| GPU | 1 × NVIDIA RTX A6000，48 GB（可用约 45 GiB） |
| 驱动 / CUDA | 595.91.07 / 13.2 |
| CPU | Intel Xeon Gold 6342 @ 2.80GHz，96 线程 |
| 内存 | 503 GB |
| 训练环境 | Python 3.12.3，torch 2.13.0+cu130，vLLM 0.32.0，transformers 5.19.0，peft 0.21.2，TRL 1.17.0.dev0（本仓库） |
| 数据生成环境（只用 CPU） | transformers 5.22.2，tokenizers 0.23.3，datasets 5.1.0，bm25s 0.3.16（见 `requirements.txt`） |
| 训练设置 | vLLM colocate + sleep mode，`vllm_gpu_memory_utilization=0.5`，bf16，gradient checkpointing，每步 4 题 × 4 条 |

注意：

- vLLM 和训练在同一张卡上，按设置 vLLM 占约一半显存。0.6B 训练本身只需几 GB，但峰值仍有 30.7–32.8 GB，可见这个峰值已经包含了 vLLM 的部分。4B + LoRA 峰值 40.6 GB，只剩约 5 GB 余量。
- 每个训练进程退出时会打印 `CUDA Error: invalid argument at cumem_allocator.cpp`，这是 vLLM sleep mode 的清理问题，发生在训练结束之后，退出码为 0，不影响结果。
- 仓库自带的环境安装脚本要求 CUDA 12.9 或 13.0，这台机器的驱动是 13.2，所以 GPU 环境是单独装的。

## 6. 结论与建议

**建议用 Qwen3-4B + LoRA 做正式实验，Qwen3-0.6B 只用来调试流程。**

- **4B 是唯一能同时满足两件事的模型。** 一是轮数稳定（每样本 8 次工具调用），能准确测 Tech 1 和 Tech 2 的耗时；二是答对率能从约 26% 学到接近 100%，能证明优化没有改变训练效果。
- **用 LoRA 不影响测试 Tech 1。** TRL 会把 LoRA 合并进模型后同步完整的 4B 权重给 vLLM，所以每轮重新加载权重的开销依然存在，而且模型越大越明显。
- **4B 不能全参数训练。** 48 GB 显存放不下 4B 的全参数训练（bf16 权重 + 梯度 + fp32 的 Adam 状态就约 48 GB，还没算激活和 vLLM）。8B 及以上更放不下。
- **0.6B 学不会做题。** 训练后能稳定跑满 K 轮，但答对率一直约为 0，只适合快速验证脚本和粗测耗时。1.7B 也不行：会跟链但不写中间值，答对率同样为 0。

数据集分工建议：

- **W1 做主实验。** 固定 P=256，扫 K 和 L_obs，测「开优化」和「不开优化」两组的每步耗时。每格跑几步即可，不需要训满。
- **W2 选 2–3 个格子做补充**，比如 K3_top3、K6_top3。
- **W3 只跑一个格子做展示。** 轮数不固定，结果按实际调用次数分组汇报。

待确认的风险：

- **大格子的显存还没测过。** 4B + LoRA 还没在 W1 最大的格子（K16、L1024、P2048）上跑过，显存余量只有约 5 GB，正式实验前需要先各跑一步确认。
- **答对率容易顶到 100%。** 4B 在 K8 上训满 50 步后接近全对，此时同组回答的奖励都一样，训练信号消失，两组曲线会重合。正确性对照建议用更难的格子（如 K16）或少跑几步。
